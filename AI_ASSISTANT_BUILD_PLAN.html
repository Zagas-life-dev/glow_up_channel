Build plan — the UP assistant

How we build it, in order

Build on hosted Gemini. Swap in the self-hosted model as the last step before production. Seven phases, each one shippable on its own, sequenced so the risky work is de-risked by the cheap work that came before it.

Revised 19 September 2026 · companion to AI_ASSISTANT_MODEL_RESEARCH.html · Next.js 16 frontend + Express/Mongo API · target model at swap: Qwen3.5-4B or Gemma 4 E4B on Cloud Run L4 · embedding is a local offline job — production hosts no embedding model

The finding that shapes this whole plan: the query language already exists.

latest-glowup-channel/src/utils/listFilters.js already defines one shared filter vocabulary across opportunities, events, jobs and resources — country, city, isRemote, isPaid, type, dateFrom, dateTo, dateField — and applyCommonFilters() already turns that object into a tested Mongo query.

So the model's job is not "understand the user". It is "fill in this exact object." We are not inventing a schema for the AI; we are pointing it at a schema our platform has used in production for months. That means no translation layer, no new query code, and — when we move to the self-hosted model — a constrained-decoding grammar we can generate directly from a file that already exists.

Second finding, nearly as useful: matchTags() in lib/nlp/taxonomy.ts already maps free text onto our interest taxonomy, deterministically, with no model at all. Phase 1 therefore ships a working recommender with zero AI in it. The model is added in Phase 2 to make it conversational — not to make it work.

00Three rules that hold for every phase

Rule 1
One query
The feed already makes ~240 round trips per request. The assistant gets one aggregation per turn. If a code review sees a loop with an await inside it touching Mongo, that is a blocker, not a nit.
Rule 2
Model behind a door
Every model call goes through lib/assistant/provider.ts. Nothing else in the codebase imports @google/genai. Phase 6 then changes one file instead of twenty.
Rule 3
Log from day one
Every turn records: user text, extracted filter, results shown, action taken. Free to collect, and it is the entire training set if we ever fine-tune. Start in Phase 1, not Phase 6.
Fix before we copy it: app/api/marketing/ai-generate/route.ts has no auth check

middleware.ts deliberately excludes /api from its matcher, and that route never validates a session. Anyone who finds the URL can POST to it and spend our Gemini quota. It is also the file we are about to use as a template, so the pattern would propagate. Every assistant route validates the BetterAuth session as its first statement, and the marketing route should get the same treatment while we are in there.

01Phase 0 — Resource text extraction

Start this first and run it alongside everything else. It is the longest lead-time item and nothing in Job C can begin without it.

Phase 0

Make the Resource PDFs readable — on a laptop, not in production

~4–6 days · parallel track

Our Resource documents store fileUrl, pdfUrl, pageCount — files, not text. Nothing can be searched or summarised until the text is out of them and chunked.

The key decision: embedding is an offline job, not a service

The embedding model runs locally, on one developer machine, through our Vulkan pipeline (~1.5–1.7x faster than CPU on that box). It writes finished vectors into MongoDB and then it is done. Production never loads an embedding model, never hosts one, and never pays for one — it only ever reads numbers that are already sitting in the database.

This is exactly what embeddingService.js was designed for when it was written: precomputed vectors on both sides, cosine similarity between two stored arrays. The stub is currently called by nothing and no model has an embedding field yet, so we are filling in a blank, not changing existing behaviour.

What runs locally, and never ships

  • EmbeddingGemma-300M GGUF weights — never committed. Git is bad at large binaries and prod has no use for them.
  • Vulkan / llama.cpp binary paths and device selection — machine-specific, stays in .env.local (already gitignored in both repos)
  • node-llama-cpp as a devDependency only — it must not enter the Cloud Run image or the Docker build gets heavier for nothing

What does get written

  • src/services/embeddingService.js — implement generateEmbedding() against the local Vulkan runner. Guard it: if the runner is absent (i.e. in prod), throw a clear error rather than falling back to something slow and silent.
  • scripts/backfill-embeddings.js — follows the existing backfill-*.js convention exactly: --dry-run, --type=, dotenv, documented usage header
  • New collection ResourceChunk — {resourceId, page, text, tags, embedding, embeddingModel, embeddingDims}
  • embedding fields on Resource and UserProfile
Two things to get right, or this bites us in six months

Stamp every vector with the model that made it. Store embeddingModel and embeddingDims next to each vector. Vectors from different models are meaningless against each other, and if someone re-runs the job later with a different model or setting, the mismatch is completely silent — the maths still works, the results just quietly get worse. The stamp is how we detect that.

Commit the script even though the weights stay out. Every other backfill-*.js in that folder is committed, and they are the record of how our data came to be the way it is. A script that exists only on one laptop means nobody else can re-embed, and when that laptop is unavailable the resource library silently stops being indexable. Keeping the script in git while gitignoring the weights and the local paths gets the full benefit of this design with none of that risk — nothing machine-specific enters the repo and the Docker image is unaffected either way.

Ships: semantic search across our own resource library, with zero production infrastructure. Feeds the main recommendation engine too — so this phase earns its keep even if the chat never launches.

The one gap this design leaves, and how we close it

Precomputed vectors work perfectly when both sides are precomputed — profile against listing, profile against resource. That covers the feed completely.

But in Phase 5 the user types a brand-new question. That question has no stored vector, and with no embedding model in production there is nothing to make one with. Worth naming now rather than discovering it in Phase 5.

The fix costs nothing and uses what we already have:

  • Tag the chunks during the same local batch job. Run matchTags() from lib/nlp/taxonomy.ts over each chunk and store the tag IDs alongside the text.
  • At query time, run matchTags() on the question instead of embedding it. It is deterministic, instant, needs no model, and returns weighted tags — so it both routes and ranks. Combine with a Mongo text index on the chunk text for the keyword half.
  • If we later want true semantic query matching, the chat GPU container is already running for Phase 6. EmbeddingGemma-300M is ~300MB and rides along in that same process for near-zero marginal cost. That is not another host — it is a rounding error inside a container that is already up.

02Phase 1 — The retrieval spine, with no AI in it

Prove the hard half works before adding the part everyone finds exciting. If this phase is not good, no model will save it.

Phase 1

Filter object in, ranked cards out

~4–5 days

One new backend endpoint that accepts the filter vocabulary we already have and returns candidates in a single aggregation, plus the frontend glue that ranks them with the engine we already have.

Backend

  • src/routes/assistant.js + src/controllers/assistantController.js
  • POST /api/assistant/search — body is the filter object; one aggregation, capped at ~60 candidates
  • Reuses applyCommonFilters() from utils/listFilters.js unchanged — no new query logic

Frontend

  • lib/assistant/extract-rules.ts — deterministic first pass: matchTags() for interests, plus simple date and country parsing
  • lib/ranking/rank.ts — call rankAndAnnotate() exactly as the feed does; the reasons it returns become the assistant's explanations for free
  • lib/i18n/translate.ts + lib/ranking/reasons.ts — reasons come out translated already
  • lib/feature-flags.ts — put the whole assistant behind a flag from the very first commit
Ships: an internal test page where you paste {"type":"scholarship","country":"NG"} and get back correctly ranked cards with readable reasons. No model, no API key, no cost. If this is slow or the ranking is wrong, stop here and fix it — everything downstream inherits both.

03Phase 2 — Gemini becomes the mouth

Now add the model, for the two jobs it is actually good at: filling the filter object, and writing the friendly text around results it was handed.

Phase 2

The chat endpoint

~5–7 days
  • lib/assistant/provider.ts — the swap point. Exposes extractFilter(text, ctx) and composeReply(results, ctx). Gemini today, self-hosted later. Nothing else touches the SDK.
  • lib/assistant/schema.ts — the filter JSON schema, written to mirror listFilters.js exactly
  • app/api/assistant/chat/route.ts — session check first, then extract → search → rank → compose, streamed back
  • lib/assistant/validate.ts — every extracted value checked against the real taxonomy and country list before it reaches Mongo
Do not copy the JSON handling from ai-generate

That route asks for JSON in the prompt, then scrapes it back with rawText.replace(/^[\s\S]*?\{/, "{") and falls back to an empty object on failure. For a marketing draft, a silent failure is harmless. For an assistant that saves things to a user's account, it is not. Use Gemini's structured-output / responseSchema mode instead — it enforces the schema server-side, and it is the direct equivalent of the constrained decoding we switch to in Phase 6. Same guarantee, same shape, both ends.

Ships: a working conversation over the API. Type a sentence, get correct cards and a warm reply. Test with curl before any UI exists.

04Phase 3 — The page

Phase 3

Chat UI and act-then-undo

~5–7 days
  • app/assistant/page.tsx + assistant-client.tsx — follows the existing home-client.tsx split
  • components/assistant/ — message list, streaming bubble, inline result cards
  • Result cards reuse the existing feed card components. The assistant should look like the platform, not like a bolted-on widget.
  • POST /api/assistant/act — save / add-to-tracker / add-to-playlist, each returning an undo token
  • SavedItem.notes already exists — write the reason into it, so a saved item remembers why it was saved
Ships: the real feature, behind the flag, for the team to use daily. Dogfood for at least a week before anyone else sees it.

05Phase 4 — The memory bank

Phase 4

Remembering, safely

~5–6 days
  • src/models/AssistantMemory.js — {userId, kind, value, confidence, sourceMessageId, createdAt}
  • Write-back into UserProfile for high-confidence facts only
  • Gate everything on UserPreferences.enablePersonalization — that flag already exists and already means exactly this. If it is off, we store nothing.
  • Liked / skipped tracking, so it stops re-suggesting rejects
  • app/assistant/memory/page.tsx — every fact listed, each one deletable
Write-back changes the feed, so it needs to be visible

A sentence typed in chat will alter what the user sees on the home feed for weeks. That is the point, and it is also the risk. Show a small "Noted: masters student · undo" chip the moment a fact is learned, and keep the memory page one tap away. Silent profile edits are the fastest way to lose someone's trust.

Ships: continuity. The assistant stops asking what it already knows.

06Phase 5 — Advice from our own library

Phase 5

Job C, unblocked by Phase 0

~4–5 days · needs Phase 0
  • POST /api/assistant/advice — no embedding call at runtime: matchTags() on the question plus a Mongo text index picks the chunks, and the model only writes prose over what came back
  • Router: is this a "find me something" turn or a "how do I" turn? Start with a keyword rule, not a model call.
  • Answers cite the resource and link to it — grounded, and it drives traffic into our own content
  • Explicit fallback: no good chunk found means "I do not have anything on that yet", never an invented answer
Ships: the assistant stops being only a search box.

07Phase 6 — The swap

Everything above ran on hosted Gemini. Now, and only now, we spend money on GPUs — with a working product and real logs to test against.

Phase 6

Self-host, test, then cut over

~6–8 days
  1. Write the 50-question test set — real questions, multiple languages, from someone who talks to users. Run it against Gemini first to get the baseline we must match.
  2. Generate the grammar from listFilters.js so the constrained decoder and the backend filter can never drift apart.
  3. Bake off Qwen3.5-4B vs Gemma 4 E4B on a rented hourly GPU — a few dollars, no commitment. Score both on the 50 questions with constrained decoding on.
  4. Build the vLLM container, weights baked into the image — this is what makes cold starts short enough for scale-to-zero to be affordable.
  5. Deploy two Cloud Run services: CPU always-warm (extract + query + rank), GPU scale-to-zero (compose + advice). No embedding model in either — the vectors are already in Mongo from Phase 0.
  6. Swap provider.ts — one file. Run the 50 questions again and compare against the Gemini baseline.
  7. Shadow-run for a week: self-hosted model answers alongside Gemini, nobody sees it, we diff the outputs. Cut over when it stops being worse.
Ships: the production assistant, self-hosted, with a measured quality comparison rather than a hopeful one.

08Phase 7 — Before it goes public

Phase 7

Hardening

~3–4 days
  • Per-user rate limits, and a hard monthly GPU spend cap with an alert well before it
  • Tune the Cloud Run idle timeout against two weeks of real instance-alive hours — not our estimate
  • Prompt-injection guard: listing text is user-submitted, so a provider could write "ignore your instructions" into a description. Treat all listing and resource text as data, never as instruction.
  • Abuse and off-topic handling, plus a visible "this is an assistant, check the official page" line
  • Confirm the flag in lib/feature-flags.ts controls a clean, total rollback

Two natural places to stop and ship

After Phase 3 — a complete, useful assistant running on Gemini, behind a flag, for a subset of users. Real feedback, near-zero infrastructure cost, nothing self-hosted yet.

After Phase 6 — the same product on our own model and our own bill. Note that the swap is not what makes it launchable. It is what makes it cheap at scale and tunable later. Do not let it block a launch that is otherwise ready.

10What we are reusing, and what is genuinely new

The reason this is five weeks and not five months.

Already built — reuse as-is
  • listFilters.js — the query vocabulary and the model's output schema
  • lib/ranking/ — scoring plus readable, translated reasons
  • lib/nlp/taxonomy.ts — matchTags() does interest extraction with no model
  • @google/genai — installed, keyed, working
  • SavedItem, ApplicationTracker, UserProfile, UserPreferences
  • Feed cards, i18n, feature flags, BetterAuth
Actually new work
  • PDF extraction and chunking long pole
  • The embedding implementation (stub exists, body does not) — local-only, never deployed
  • One assistant endpoint and its single aggregation
  • The provider abstraction and filter schema
  • Chat UI and undo flow
  • AssistantMemory and its review screen
  • vLLM container and Cloud Run GPU service
