Model research — the UP assistant

Which small model should run the chat?

Ten models compared for one specific job: a friendly assistant that finds opportunities in our own database, explains why they fit, and saves them for the user. Self-hosted, on a startup budget.

16 September 2026 · for the Glowup/UP team · decisions already taken: self-host · Cloud Run + L4 GPU · act-then-undo · advice from our own Resource library

Short version — Qwen3.5-4B. Budget about $80/month. And the model is not the risky part.

Pick Qwen3.5-4B. It is Apache 2.0, free to use commercially, and it wins on the one number that actually predicts success here: instruction-following. It scores 89.8% on IFEval — higher than GPT-OSS-120B, a model thirty times its size. Our assistant mostly needs to follow format rules and stay inside the facts we hand it. That is an instruction-following job, not a genius job.

Gemma 4 E4B is a very close second and nobody would be wrong to take it instead. It went Apache 2.0 in April, it is a Google model running on Google Cloud, and it has native tool-calling built in. If deployment friction turns out to be the real problem, switch. Keep the prompts model-agnostic so that stays a one-line change.

The real risk is not model quality — it is small models producing broken JSON. Measured parse rates on comparable models range from 26% to 96%. That is the difference between a product and a toy. The fix is free and takes an afternoon: constrained decoding (§05). Do not skip it.

And the real cost driver is not tokens — it is how long the GPU stays awake. Cloud Run bills per second of instance life, not per word generated. Bursty evening traffic costs ~$80/month. The exact same number of chats spread thinly across the day costs ~$320/month. Same users, four times the bill (§04).

01What the model actually has to do

Before comparing models, be clear about the job. Most teams over-buy here because they imagine the model doing everything. Ours does three narrow things, and only one of them is hard.

Job A · every turn
Fill a form
"I need scholarships to apply for" becomes {type:"scholarship", country:"NG", educationLevel:"masters"}. Pure translation. A 2B model does this well. Easy.
Job B · every turn
Talk about results
Our existing ranker in lib/ranking/ already picked the top five and already produced the reasons. The model just writes friendly sentences around facts it was handed. Medium.
Job C · sometimes
Give advice
"How do I approach this essay?" — answered from our own PDF resources, not from the model's memory. Needs real reading comprehension. This is the job that sets the size.

Two things follow from this, and they save us a lot of money.

  • The model never searches and never ranks. MongoDB searches. lib/ranking/ ranks. The model only ever sees results that were already chosen. It physically cannot invent a scholarship, because it never sees anything except the handful of cards we pass it.
  • The model never needs world knowledge. Everything factual comes from our database or our own resource PDFs. So all the benchmarks about trivia, history and general knowledge — the ones that make big models look necessary — simply do not apply to us.
Why this means a 4B model is genuinely enough

A small model's main weaknesses are that it knows less about the world and reasons less deeply. We have designed both weaknesses out of the job. What is left — following a format, staying on topic, being warm, summarising a passage we handed it — is exactly what small models became good at this year.

Also looked at, and why not

  • gpt-oss-20b (21B total, 3.6B active, runs in 16GB, roughly o3-mini quality) — genuinely the strongest thing on this list, and it does fit an L4. But it is five times the model for a job we deliberately made small, and every extra GPU-second is money. Revisit only if we later want one model handling everything including hard reasoning.
  • Gemma 4 26B-A4B and 31B Dense — the 26B only activates 3.8B parameters per token, so it runs faster than its size suggests, but the full weights still have to sit in VRAM. Overkill, and it squeezes out KV-cache room we would rather spend on concurrent users.
  • Llama 3.2 3B — measured at a 47.8–56.5% JSON parse rate. See §05. Not viable for a tool-calling assistant without heavy scaffolding.
How to read every number in that table

Benchmarks are marketing as much as measurement, and each vendor publishes the ones it wins. Treat this as a shortlist, not a verdict. Budget two days to test the top three on fifty real user questions written by someone on the team who talks to users. That test will tell us more than every number above combined, and it costs almost nothing to run.

04What it actually costs on Cloud Run

This is the section to read twice. Cloud Run GPU billing surprises people, and the surprise is expensive.

The rate. An NVIDIA L4 on Cloud Run in a Tier 1 region is about $0.0001867 per second without zonal redundancy — roughly $0.67 per hour. With zonal redundancy it rises to about $0.0002909 per second. For an assistant feature, skip zonal redundancy; if it is briefly down, the rest of the platform still works.

The trap: you are billed for instance lifetime, not for tokens

GPU-enabled Cloud Run keeps CPU allocated for the whole life of an instance, and you pay per second for every second it is alive — not just the seconds it is generating text. So the bill is driven by how long the GPU stays awake, not by how many people chat. Scale-to-zero only saves money when traffic arrives in clumps. Thinly spread traffic keeps the instance permanently warm and you pay nearly the always-on price for very few conversations.

Bursty · realistic
~$80/mo
Traffic clumps into evenings. Instance alive ~4 hrs/day. This is what we should be aiming for, and it is achievable with a short idle timeout.
Thinly spread · the trap
~$320/mo
Same number of chats, arriving one at a time across 16 hours. Instance never gets to sleep. Four times the cost for identical usage.
Always on · the ceiling
~$480/mo
24/7, no scale-down. This is also roughly what a dedicated GPU VM costs — which is the point: past a certain traffic level, serverless stops being cheaper.

Estimates. The $0.67/hr rate is published; the monthly figures are our own arithmetic from assumed instance-alive hours and should be re-checked against real traffic after two weeks in production.

The three levers that control this bill

  1. Idle timeout. The single biggest dial. Short timeout means the GPU sleeps sooner and we pay less, but more users hit a cold start. This is the tradeoff to tune, and it should be tuned with real numbers, not guesses.
  2. Bake the weights into the container image. If the model downloads at boot, cold starts run into tens of seconds and we will be tempted to keep the GPU warm — which is what costs money. Weights in the image make cold starts short enough that aggressive scale-down becomes affordable. Measure this on day one; the whole cost model depends on it.
  3. Split the jobs across two services. Explained below. This is the trick that makes cold starts nearly invisible.

The two-service trick

Run two Cloud Run services instead of one:

  • A CPU-only service, always warm, costing cents. It hosts a 0.8B model doing Job A — turning the sentence into a filter — plus the database query and the existing ranker. No GPU involved.
  • A GPU service that only wakes for Jobs B and C — the actual talking.

The user sends "I need scholarships". Within a second the CPU service has parsed it, queried Mongo, ranked results, and streamed back the cards themselves plus a line like "Found 6 scholarships you can still apply for — let me look at these properly." The GPU boots in the background and the friendly commentary arrives a moment later. The cold start disappears behind content the user is already reading. And on the many turns that need no commentary at all, the GPU never wakes and costs nothing.

05The thing that will actually break: JSON

If one section of this document gets implemented, make it this one. Small models are not unreliable because they are stupid. They are unreliable because they drift out of format.

Measured JSON parse rates on comparable small models:

ModelValid JSON producedWhat that means in practice
Qwen2.5 1.5B95.7%Roughly 1 in 23 turns breaks. Noticeable but survivable with retries.
Qwen2.5 0.5B82% recoverableAnd only 72% once the arguments are checked too. So more than a quarter of tool calls are wrong in some way.
Llama 3.2 3B47.8–56.5%About half of all actions fail. Unusable for save-and-track.
SmolLM2 1.7B26.1%Three quarters of attempts are broken. Completely unusable.
The fix costs nothing and takes an afternoon

Constrained decoding. Instead of asking the model nicely for JSON and hoping, we constrain what it is allowed to produce at each step so that only characters valid under our schema can come out. Invalid JSON becomes impossible, not unlikely. vLLM ships this as guided decoding; llama.cpp does it with GBNF grammars. Either way it is configuration, not a research project.

With it, parse rate is 100% by construction. Model quality then only affects whether the values are sensible — a much smaller and much more forgiving problem. This is what makes a 4B model production-viable and it is why we can ignore most of the scary numbers in the table above.

Belt and braces

  • Validate on our side anyway. The model may emit {"country":"Wakanda"} — perfectly valid JSON, meaningless value. Validate every extracted field against our real taxonomy in lib/nlp/taxonomy.ts before it reaches Mongo.
  • Every action is reversible. We already chose act-then-undo. That choice is doing real work here: a wrong save costs the user one tap, not a support ticket.
  • Log every extraction. Query in, JSON out, and whether the user seemed happy. This is the training data for §07, and it is free to collect from day one. Start collecting before we need it.

06The embedding model — and a stub we can finally fill

Job C needs semantic search over our Resource library. That needs an embedding model, which is a different and much smaller thing than the chat model.

latest-glowup-channel/src/services/embeddingService.js has been sitting there as an unimplemented stub, throwing on call, with a comment listing providers to choose from. This is the moment to finish it — and doing so improves the main feed too, not just the chat.

ModelSizeDimensionsVerdict
EmbeddingGemma-300M Pick 300M 768 Runs in under 200MB RAM quantized, embeds in ~22ms, trained on 100+ languages with real cross-lingual retrieval. Runs on the CPU service — no GPU, effectively free. Rivals much larger models on MTEB.

One piece of work nobody has costed yet

Our Resource documents are PDFs — the model stores fileUrl, pdfUrl, pageCount, not text. Before anything can be embedded, the text has to be extracted and chunked. That is a real task: a batch job, a text store, a re-run whenever a resource is added. It is not hard, but it is the actual critical path for Job C and it should be scheduled explicitly rather than discovered late.

07Fine-tuning: not yet, and cheaper than expected

Self-hosting was chosen partly to keep fine-tuning open. Good. But fine-tuning first is a common and expensive mistake.

Do not fine-tune at launch. On day one we have no data about how our users actually phrase things, and fine-tuning on guesses bakes in the guesses. Prompting plus constrained decoding will carry us a long way. Log everything, then train on reality.

When the time comes, it is cheap. A LoRA or QLoRA run on a 7–8B model costs $3–$10 in GPU time — two to four hours on a rented A100 at around $1.50–$2.00/hr. A 4B costs less. This is not a budget line item; it is a rounding error. The expensive part is assembling and cleaning the examples, which is human time.

Teaching it our format & tone
~200 examples
Output formatting is the cheapest thing to teach. A couple of hundred good examples of "user said X, correct filter is Y" is enough to move the needle. Realistic within a month of logging.
Teaching it our categories
2,000+ examples
Classifying into ~20 domain categories needs an order of magnitude more. This is the harder ask, and a good reason to lean on our existing lib/nlp/taxonomy.ts rather than teaching the model to replace it.

The sequence that works: ship with prompting → log query-and-outcome pairs for four to eight weeks → look at where it actually fails → LoRA on those specific failures for about $10 → measure against the same fifty test questions. Repeat only if the numbers justify it.

08Recommended order of work

Sequenced so that the expensive, irreversible decisions come last, after cheap experiments have answered them.

Step 1 · costs nothing
Build the whole thing on hosted Gemma

Use the @google/genai path already in the repo. No GPU, no ops. Get the tool schema, the prompts, the memory bank and the act-then-undo flow working end to end. Everything learned here transfers to the self-hosted model unchanged.

Step 2 · one afternoon
Write the fifty-question test set

Real questions, from someone who talks to users, in more than one language. This becomes the thing every later decision is measured against. Without it, model comparison is vibes.

Step 3 · the real critical path
Extract and chunk the Resource PDFs

Job C cannot start until this exists. Stand up EmbeddingGemma on CPU and finally implement embeddingService.js. This improves the main feed as a side effect, so it earns its keep even if the chat slips.

Step 4 · two days
Bake off Qwen3.5-4B vs Gemma 4 E4B

Rent a GPU by the hour — a few dollars, not a monthly commitment. Run both against the fifty questions with constrained decoding on. Pick the winner on results, not on this document.

Step 5 · the first real bill
Self-host on Cloud Run, two services

Weights baked into the image. CPU service always warm, GPU service scaling to zero. Then watch the actual instance-alive hours for two weeks and tune the idle timeout against the real number, not our estimate.

Step 6 · month two or later
Consider a LoRA, for about $10

Only after there is logged data showing where it actually fails. Not before.

One carry-over risk from the existing platform

The feed already makes roughly 240 database round trips per request. If a chat turn fans out the same way, replies will take ten seconds and feel broken regardless of which model we pick. The assistant's database lookup has to be a single aggregation. No model choice can rescue a slow query, and this is the most likely cause of a disappointing first demo.
