The main problems:

  • One field doing four jobs. tags mixes topics (sales), places (lagos), company names (oshwal college) and junk (job, other, lang:fr). The ranking treats all of them the same.
  • The same thing spelled many ways. tech/technology, graphic design/graphics design/graphicdesign, skillsdevelopment/skill development/skillbuilding, plus typos like stroytelling.
  • Three overlapping fields. tags, industrySectors and targetAudience all partly describe the same things.
  • Location is saved only in the browser. The app already works out where each user is (GPS, IP, profile), but only stores it on their device. That is why there are no location analytics.

3 · The new tag list (126 tags)

Tags are split into 7 groups. Each group answers one question about a listing, so a place can never be mistaken for a topic again.

Listing type 17 · Industry / field 25 · Skills 54 · Community groups 12 · Career level 4 · Event format 9 · Work arrangement 5

Community groups, in plain English. Most tags say what a listing is about. A community group says who it is for: the kind of person who would see it and think "this is meant for me".

Take a photography workshop. What it's about: photography and training. Who it's for: creatives. These are different, and both matter. A woman founder in Lagos wants to find everything aimed at women founders, whether it's a grant, a networking night or a finance course, even though those are all different topics.

The rule: a listing only gets a community group when it is deliberately aimed at that group. An ordinary accounting job is not tagged "Women" just because women can apply. A "women in finance fellowship" is. Users choose their own groups during onboarding, and the feed gives a boost to listings aimed at those groups.

How to read the tables: Listing uses and Profile uses show how often the old raw values that merge into each tag were used. The last column shows real values from your database that will become that tag.

4 · Cleaning up existing data

Every existing raw value falls into one of four buckets:

  • Mapped: becomes one or more official tags. For example, women entrepreneurs becomes Women + Founders & entrepreneurs.
  • Place: a location, like lagos or nairobi. It moves into the listing's location fields, and is not a tag.
  • Dropped: says nothing useful (job, other, lang:fr, "candidates with 3–5 years…").
  • Unmapped: mostly company names and one-off words. These listings go through the auto-tagger instead.

How tags and scores merge

  • Per-user interest scores (the user_hashtag_affinity table, which drives about half the feed score) are added together when their tags merge. A user with a score of 4 on tech and 2 on technology gets 6 on Technology & software.
  • Usage counts are recounted from the real listings and profiles, not added up from the old counters. The earlier hashtag review found the old counters had been inflated before, so recounting is the only way to get true numbers.
  • Each clean tag records where it came from: migration, rule, ai or provider. That is what lets admins see AI-made tags.
  • The cleanup script shows a dry run first and only writes to the database when run with --apply, the same way repair-hashtag-data.js did.

5 · Automatic tagging (our own rules, free)

This runs every time a listing is created or edited, and once over all existing listings.

  1. Read the title, description and any old tags.
  2. Detect the language, using the existing lib/nlp/detect-language. Each official tag has keywords in every supported language (e.g. French bourse → Scholarship, Swahili ufadhili wa masomo → Scholarship).
  3. Find keywords and look at the words around them to decide which meaning is meant. For example, "education":
    • near teacher, curriculum, school, lecturer → Industry: Education (a job in education)
    • near learn, course, bootcamp, certificate, training → Type: Training programme / Course (a way to learn)
    • near tuition, fees, study abroad, university admission → Type: Scholarship
  4. Score each tag. A match in the title counts more than one in the description, and a word repeated counts more than a single mention.
  5. Apply the limits: 1–2 industries, up to 5 skills, up to 3 community groups. The strongest matches win.
  6. Check completeness. Every listing needs a type and an industry, and jobs also need a career level. If one is missing, or the listing has 3 tags or fewer, it goes to the AI step.

Providers see the suggested tags when they post and can add or remove them, but only from the official list. Profile skills work the same way: autocomplete from the list, and any free-typed skill is mapped or dropped.

6 · The AI step

The rules finish. If the listing has 3 tags or fewer, or misses a required group, it goes to the AI queue. Listings with good rule-based tags never touch the AI.
We send Gemini the title, description and the rule-based tags as hints, plus the official tag list. We only send public listing text, never user data.
If Gemini errors, times out or hits its free limit, we send the same request to Mistral.
We check the answer: any tag not on the official list is thrown out, and the limits are applied. The result replaces the listing's tags, marked as AI-made (visible to admins only).
If both fail, the listing keeps its rule-based tags, is marked "needs AI", and a nightly job tries again.

The provider code sits behind one small interface: tag suggestions in, official tags out. Switching to a self-hosted model later means changing one file. Gemini is already set up in the frontend (app/api/marketing/ai-generate/route.ts). The backend will need its own GEMINI_API_KEY and a MISTRAL_API_KEY.

7 · Languages

  • Supported: English, French, Spanish and Portuguese (already built in lib/i18n), plus Swahili and Amharic (new). Arabic comes later. It reads right-to-left, so the layout has to mirror.
  • Whole app translated for users, providers and monitors. Today only part of the app is translated, so this is the biggest single piece of work. Admin screens stay in English.
  • Tag names are stored once, as an ID like industry:finance, and shown in the user's language, e.g. "Finance, banque et comptabilité".
  • How translations are made: the AI translates once, and the results are saved in the language files, so nothing is translated on every page load. A second AI pass checks each translation and flags doubtful ones. You review French. Swahili and Amharic get a native-speaker check before we promote those markets, which is the one open risk here.
  • Listing text (descriptions written by providers) stays in its original language. Only the app around it is translated.

8 · User location

What already exists: /api/geo reads the country and city Vercel attaches to each visit (free, no permission, no IP stored). hooks/use-user-location.ts combines GPS, IP and profile location, and lib/geo/distance.ts ranks listings by distance. The missing piece is saving it to the server.

Where a user's location comes from (best first)

  1. GPS from the device, if the user allows it. The most precise.
  2. IP location from Vercel. Always available, accurate to country and roughly to city.
  3. Profile country, state and city, now picked from lists instead of typed freely.

What we store

  • Country (the most important), state, city, which source it came from, when, and coordinates rounded to about 1 km. We never store the exact GPS point or the IP address.
  • Logged-in users: saved to their account, and refreshed when they move to another city or country.
  • Visitors: kept in their browser, and attached to their account when they sign up. Their visits count in analytics only as anonymous totals.
  • Users can clear their saved location in settings.

Existing messy profile locations

Country spellings are fixed automatically (nigerai, ng, 🇳🇬 → Nigeria). niger is flagged for review, because Niger is a real country. Neighbourhoods roll up to their city and state (Ikeja, Lekki, Yaba → Lagos; Kubwa, Gwarinpa → Abuja FCT). Users are asked once to confirm, with the picker pre-filled from our best guess.

Asking for location on first load (wording for your review)

Browsers let a site show their permission prompt only once. If someone clicks "Block" there, only they can undo it in their browser settings. So we show our own short explanation first, and only trigger the browser prompt when they tap "Allow".

Find opportunities near you

UP uses your location to show jobs, events and scholarships in your country and city first, and to hide ones you can't apply for. We only save your approximate area, never your exact position, and you can turn this off any time in settings.

Allow locationNot now
  • "Not now" on our screen: the browser prompt was never used, so a "Use my location" button in the feed can ask properly later. We don't show the screen again automatically.
  • "Block" on the browser's prompt: the same button shows 3 short steps for turning location back on in their browser.
  • Either way, IP location keeps working, so the feed is still local at country level.
  • This screen is translated like the rest of the app.

9 · Listing location

User location comes from the device, so listings need to be precise to be matched against it.

  • Providers pick from lists: country (required), state (required unless remote), city (optional).
  • Coordinates come from a built-in list of cities and states, so every listing gets a map point without any paid map service.
  • Remote listings pick which countries can apply, e.g. "Remote · Nigeria only" or "Remote · anywhere in Africa". Users outside those countries don't see them.
  • Existing listings are filled from their current location fields and old place tags (lagos, nairobi…). Where those are empty, the listing goes on an admin "location missing" list to be filled in by hand. The AI never writes location.

10 · Location analytics

WhoSees
AdminsEverything: users by country, state and city (signups, active users), views, clicks and applications by location for every listing, and supply vs demand (where users are compared with where listings are).
ProvidersTheir own listings only: where views, clicks and applications came from, e.g. "40% of views came from Lagos". Totals only, never individual users.
MonitorsThe same as providers, but only for the listings assigned to them (the existing MonitorAssignment records). Read-only.

To protect privacy, any location with fewer than 5 people is shown as "Other", so nobody can be picked out in a small town.

11 · What gets built

  1. Tag list as code: the list above, with translations and keywords for each language, used by both the backend and the frontend.
  2. Cleanup script: dry run, then --apply. Fills the new clean-tag field, merges interest scores, recounts usage and moves place tags into location fields.
  3. Rule-based auto-tagger: runs on create/edit, with the AI queue behind it (Gemini → Mistral → nightly retry).
  4. Provider posting form: tag picker limited to the list, with suggestions; structured location picker; remote countries.
  5. Profile and onboarding: skills and community groups picked from the list; location picker; the one-time "confirm your location" prompt.
  6. Location capture: the first-load explanation screen, the fallback button, and saving to the server (accounts plus anonymous totals).
  7. Ranking switch-over: backend feed and lib/ranking/ move to the clean tags; distance ranking uses listing coordinates.
  8. Analytics dashboards: admin, provider and monitor views.
  9. Translation: the whole app for users, providers and monitors, in 6 languages.

12 · Things to watch

  • Free AI tiers. On Google's free tier, what you send may be used to improve their products. That's acceptable only because we send public listing text and nothing about users. Free tiers also have rate limits; the nightly retry covers bursts.
  • Swahili and Amharic quality. AI translation is decent but not perfect, and nobody on the team reads these yet. Get a native speaker to check before any marketing in Kenya or Ethiopia.
  • The whole-app translation is the largest part of this work. It touches almost every screen.
  • Supply gap. Most users are in Nigeria, but most jobs are in Kenya and Ethiopia. Location ranking will make that visible to users: Nigerian users will see fewer nearby jobs. The analytics will show admins exactly where to source more.
  • Tag list upkeep. Because tags are strict, new fields (e.g. a new industry) need an admin to add them to the list. Unmapped provider tags are logged, so gaps are easy to spot.
