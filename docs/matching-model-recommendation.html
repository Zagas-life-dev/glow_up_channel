Self-hosted matching, built to scale

10,000 users and growing. No per-call metering. The model runs on your own infrastructure, and the bill stops tracking your user count.

The stack

granite-embedding-311m-multilingual-r2 on TEI, Cloud Run

$0/month today · ~$18/month at 100K users · flat, not per-call

Hugging Face's Text Embeddings Inference is the server — a Rust binary purpose-built for this, with batching, ONNX on CPU, Prometheus metrics and OpenTelemetry already in it. You do not write an inference server; you run their image with a --model-id flag.

That removes the main argument against self-hosting. The work is a Dockerfile of about five lines and one more Cloud Build step.

You are right about the trajectory

Metered APIs price per call, so the bill grows exactly as fast as you do. Self-hosted compute prices per container, and one container absorbs an enormous amount of growth.

Why TEI rather than rolling your own

  • It is the server. HTTP /embed endpoint, dynamic batching, health and metrics endpoints, graceful shutdown. Writing this yourself in Node means onnxruntime-node, your own batching, and your own concurrency control.
  • Its CPU path is ONNX Runtime with Intel MKL, which is materially faster than naive per-request inference. HuggingFace document 10×+ throughput over naive Python serving.
  • Granite R2 is ModernBERT under the hood, which TEI supports natively, and IBM ship pre-converted ONNX and OpenVINO INT8 weights alongside the PyTorch ones — the INT8 CPU path is exactly what you want here, and you convert nothing yourself.
  • It is language-agnostic to your stack. Your backend stays pure Node and talks to it over HTTP. No Python in your deploy, no native bindings in your Express image.

Which model to point TEI at

TEI only serves architectures it knows: BERT, CamemBERT, XLM-RoBERTa, NomicBERT, JinaBERT, MPNet, ModernBERT, Mistral, Qwen2/Qwen3 and Gemma3. That rules out a few shortlist entries outright, so compatibility comes before benchmarks.

Granite 311m R2 is the pick, and it displaces EmbeddingGemma from the earlier draft on four specific grounds that only became clear once TEI and CPU serving were the constraints:

  • 32K context against EmbeddingGemma's 2K. Your listing bodies are the bulk of each document — recommendationService.js notes description is 60–70% of a resource. 2K tokens means chunking or truncating them; 32K means you do not think about it.
  • Pre-built OpenVINO INT8 weights. IBM ship an INT8 CPU build alongside the PyTorch and ONNX ones. That is the deployment path you are actually on, already quantized, with no conversion step to own.
  • Apache 2.0 rather than the Gemma licence terms, which carry a field-of-use rider you would have to read properly before shipping commercially.
  • 65.2 MTEB retrieval, #2 among open models under 500M. EmbeddingGemma still ranks #1 in that class, so this is a real if modest quality concession — traded for context length, licence and a ready INT8 path.

All four of your languages — English, French, Spanish and Portuguese — are in Granite's 52-language enhanced-support set, not just its long tail of 200+.

The throughput alternative

granite-embedding-97m-multilingual-r2 is the same family, roughly 3× faster, and scores 60.3 against the 311m's 65.2. It also emits 384 dimensions natively, which halves your Mongo storage and wire cost with no truncation step at all. If you would rather have 3× the per-container headroom than the last 5 MTEB points, take this one — it is a defensible pick, not a downgrade.

Correction to something I said earlier: I described the strong small rerankers as English-only. That is wrong — Alibaba-NLP/gte-multilingual-reranker-base covers 70+ languages including all four of yours, runs on TEI, takes 8K context, and is encoder-only, which its authors put at ~10× the inference speed of decoder-based rerankers of similar quality. If you add a reranking stage later, that is the one to use, not the English-only Ettin or ModernBERT variants.

What to deploy

embeddings/Dockerfile 
FROM ghcr.io/huggingface/text-embeddings-inference:cpu-1.8.1

# Bake the weights into the image so cold start does not wait on a download.
ENV MODEL_ID=ibm-granite/granite-embedding-311m-multilingual-r2
RUN text-embeddings-router --model-id $MODEL_ID --dtype float32 --pooling mean --download-only

ENV PORT=8080
ENTRYPOINT ["text-embeddings-router"]
CMD ["--model-id", "ibm-granite/granite-embedding-311m-multilingual-r2", \
     "--dtype", "float32", "--pooling", "cls", \
     "--port", "8080", "--max-batch-tokens", "16384"]
deploy 
gcloud run deploy glowup-embeddings \
  --image gcr.io/$PROJECT_ID/glowup-embeddings:$COMMIT_SHA \
  --region us-central1 \
  --cpu 2 --memory 2Gi \
  --min-instances 0 --max-instances 10 \
  --concurrency 32 \
  --no-allow-unauthenticated

# Only the backend may call it.
gcloud run services add-iam-policy-binding glowup-embeddings \
  --member serviceAccount:$BACKEND_SA --role roles/run.invoker

--concurrency 32 rather than the 4 you would use for naive inference: TEI batches internally, so letting requests queue into a batch is how you get its throughput. --no-allow-unauthenticated matters — unlike your public API, nothing outside the project should reach this.

Capacity, for context: one 2-vCPU TEI container running Granite 311m should sustain low tens of embeddings per second with batching — call it 1–4M/day. That covers your uncached traffic well past 100K users on a single instance, and --max-instances 10 handles bursts above it. This is an estimate from model size, not a measurement; TEI exposes Prometheus metrics, so you will know the real number the day you deploy.

The backend changes

  1. Fill in src/services/embeddingService.js. The stub at line 34 already throws "not implemented, please configure an embedding provider". It becomes a fetch to the Cloud Run URL with an ID token. It currently references post.embedding and suggests OpenAI defaults — posts are the deprecated surface, so retarget it at resources.
  2. Backfill the corpus once. A Cloud Run Job on the same image, or a one-off script next to your existing scripts/. TEI takes batched input, so send listings in chunks of 32 rather than one at a time.
  3. Embed new listings on a cron. You already run five node-cron jobs in-process; add one that picks up any resource missing a vector.
  4. Cache the user vector on the profile. Recompute in the routes/profile.js write path when interests change — never on read. This is the single highest-leverage line in the plan. It decouples embedding volume from user count: 10K users generate roughly 100–200 profile edits/day, not 30,000 renders. It is why the "cached" column above stays flat while everything else grows.
  5. Cosine in JS, in the loop you already have. Add it beside calculateInterestMatch at recommendationService.js:848 as one more weighted term. SCORING_CANDIDATE_CAP is 400 and your own comment puts real volume near 100 per type, so a dot product over 400 × 256 floats is sub-millisecond and needs no index.
  6. Store 256-dim Float32 as BSON Binary. Mongo stores a JS number array as 8-byte doubles, so 768 dims costs ~6 KB per doc — 2.4 MB extra on the wire per 400-doc pull. Binary at 256 dims is ~1 KB. Granite 311m is Matryoshka-trained (512/384/256/128), so truncating 768→256 costs 1–3% recall and can be undone later without re-embedding.

Two hard rules. This must be a separate Cloud Run service, never added to the Express container — that runs --concurrency 100 --cpu 1, and synchronous inference on Node's event loop would stall every request on the instance. And nothing on the feed read path may call it: the known bottleneck is ~240 round trips per request at 296 ms RTT, so an embedding hop during a render would worsen the real problem to fix a smaller one. Both vectors are in Mongo before scoring starts.

Skip Atlas Vector Search for now. src/config/database.js:425–446 carries commented setup for a $vectorSearch index on posts.embedding at 1536 dimensions. Posts are deprecated, 1536 is an OpenAI ada-002 shape matching nothing here, and brute force beats an index hop at 400 candidates. It also needs an M10 tier, roughly $57/month. Revisit past ~50,000 listings — which, at your growth rate, is a real date rather than a hypothetical.

The scaling path, in order

  1. Now → 100K users: exactly as above. min-instances 0, free tier, cold starts land on cron jobs where nobody notices.
  2. When you add live query embedding (search-as-you-type, say), cold start starts mattering. Move to min-instances 1 ($71/mo) or, cheaper, a e2-small VM at $12.23 running the same image.
  3. Past ~50K listings: add the Atlas vector index, or swap the JS cosine for a pre-filtered candidate set. Not before.
  4. Past ~1M users: the flat-rate VM path (a couple of e2-standard-2 at $30.82 each on committed use) undercuts Cloud Run's per-second premium. Same container, different substrate.

Caveats. Throughput and latency figures are estimates scaled from model size, not measured on GCP hardware — they drive the capacity headroom claim, so treat that claim as directional until TEI's own metrics confirm it. The user-scale projections assume ~3 feed renders per user per day and ~1–2% of users editing their profile daily; both are assumptions about your product, not measurements from it, and the cost table moves proportionally if they are wrong. The metered-API column uses $0.15/1M tokens at 64 tokens per call for comparison only. Cloud Run free-tier allowances are per billing account and your Express backend already draws on them, so verify the headroom in Cloud Run metrics before relying on the zeros.
