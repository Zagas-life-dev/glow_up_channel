Small models for AI matching

Ranked shortlists by parameter budget, scoped to models that work out of the box with zero training, and to the four languages lib/nlp/detect-language.ts supports — en · fr · es · pt.

The load-bearing correction: all three models currently in C:\llama.cpp\models are generative decoder LLMs. Matching is a retrieval problem, not a generation problem.

An embedding model turns each listing into one vector once at ingest, and matching becomes a cosine — the exact operation lib/nlp/similarity.ts already performs over tag maps. A generative model has to run a full forward pass per user–item pair, which at a few hundred items per feed render is not a latency budget that exists. It is also the family that actually delivers on “zero training”: embedding models are contrastively trained for similarity, whereas a 270M generative model is sold as a fine-tuning base.

So: embed for matching. Rerank the top ~30 if you want more. Keep the generative models for a different job entirely — see the last section.

Your three local models

Included as requested, judged against the actual job.

Not for matching

gemma-3-270m-it · Q4_K_M · 253 MB

Google's own framing is that it is “a high-quality foundation model… once specialized through fine-tuning” for classification and extraction — which is precisely the zero-training constraint it fails. Best-in-class IFEval for its size, so it follows instructions; it just does not know enough to judge relevance unaided. Its 262K-token vocabulary is also why it is heavier on disk than the 350M model sitting beside it.

Adjacent use

LFM2-350M · Q4_K_M · 229 MB

Liquid's LFM2 line is built for fast CPU/edge decoding, and it is the quickest generator you have. Wrong family for scoring pairs, but a fair fit for the one genuinely generative job in this pipeline: turning a SignalBreakdown into a natural “why you're seeing this” line in the user's language, replacing the templated strings in lib/ranking/reasons.ts.

Adjacent use

Qwen3.5-0.8B · Q4_K_M · 532 MB

The most capable of the three and the only one with enough headroom for reliable zero-shot structured output. Use it offline at ingest — read a listing, emit taxonomy tag ids as JSON — to catch vocabulary taxonomy.ts has no alias for. That is a batch job, not a per-render one. Note that its embedding sibling, Qwen3-Embedding-0.6B, tops two tiers above.

Where this lands in the codebase

The pipeline is already shaped for this. semanticSignal in lib/ranking/signals.ts consumes a 0–1 similarity, and cosineSimilarity in lib/nlp/similarity.ts already computes cosine over sparse maps. Swapping in a dense vector is a substitution at one seam, not a rewrite.

ingest  -->  embed(title + body)  -->  store vector on the listing   (once, offline)
profile -->  embed(interests)     -->  cache in localStorage        (once per profile edit)
render  -->  cosine(user, item)   -->  semanticSignal               (pure, sync, microseconds)

Two constraints worth holding onto:

  • Keep signals.ts pure and synchronous. Its header states the reason outright. So embedding has to happen outside ranking — vectors arrive precomputed, and the hot path only ever does arithmetic.
  • Don't delete the taxonomy. It is what lets reasons.ts say which interest matched; an embedding gives you a number with no explanation. Run the vector score as an added signal in weights.ts and let the existing null-dropping renormalization handle items that have no vector yet — that behaviour means you can roll this out incrementally without a backfill gate.

If you want the shortest path: EmbeddingGemma-300M at 256 truncated dimensions. It is #1 in its class, it is Matryoshka so the dimension choice stays reversible, its 2K context comfortably covers title + tags + lede, and it is the same model family as the Gemma already on your disk. Fall back to granite-embedding-97m-multilingual-r2 if you decide to run embeddings in the browser rather than at ingest.

Caveats. MTEB standings move month to month, and several figures here come from vendor announcements and secondary benchmark write-ups rather than independent replication — treat the tier orderings as sound and the individual decimals as indicative. Nothing here was benchmarked on Glowup Diaries data; the only number that settles the pick is nDCG on your own labelled pairs. Licences were read from model cards, not from counsel.
