Where on Google Cloud to run it

Every GCP surface that can host a model, priced for these models at 10,000 calls/day. Not APIs — places you deploy weights.

Answer

Cloud Run — a second service, CPU only, scale-to-zero

$0.00/month · inside the free tier at your volume

You already have the pipeline: cloudbuild.yaml, a Dockerfile, and gcloud run deploy in your npm scripts. A second service is the same deploy you already run, pointed at a different image. Same project, same region, same IAM, one more entry in Cloud Build.

Everything else on Google Cloud that can host a model either bills you for idle hours (Vertex Endpoints, GKE) or hands you a GPU you have no use for (Cloud Run GPU). None of these models needs a GPU — the largest is 595M parameters and runs in under 100 ms on a CPU core.

Cold start is the only real trade-off, and your architecture makes it disappear. Both embedding events — a listing being ingested, a profile being edited — are background writes, not feed renders. A 5-second cold start on a cron job costs nobody anything. Nothing on the read path ever waits for this service.

Bake the weights into the container image rather than fetching from GCS at boot. It makes the image bigger and the cold start much shorter, and image storage is ~$0.10/GB/month.

Do not deploy from Vertex AI Model Garden's one-click button. EmbeddingGemma, BGE-M3 and the Qwen embedding models are all in Model Garden, and the deploy button provisions a dedicated Vertex Endpoint — a node billed by the hour whether or not anything calls it. That is $45–89/month for a workload the free tier would carry. Pull the weights from Model Garden or Hugging Face, put them in your own image, deploy to Cloud Run.

Still true regardless of platform: this has to be a separate Cloud Run service, not added to the Express backend. That service runs --concurrency 100 --cpu 1, and synchronous ONNX inference on Node's event loop would stall every other request on the instance. Separate service, separate scaling, separate failure domain.

What to deploy

  1. New service: glowup-embeddings. Its own Dockerfile with the ONNX weights baked in, its own cloudbuild.yaml step, deployed with --cpu 2 --memory 2Gi --min-instances 0 --concurrency 4. Low concurrency on purpose: inference is CPU-bound, so queueing beats thrashing.
  2. Make it internal-only. --no-allow-unauthenticated and grant the backend's service account roles/run.invoker. Unlike your public API, nothing outside the project should reach it.
  3. Cloud Run Job for the backfill. One pass over existing resources to populate vectors, triggered manually or by Cloud Scheduler. Same image, different entrypoint.
  4. Call it only from writes. The ingest cron in src/services/ and the profile-update handler. Never from a feed render.

Caveats. The Vertex AI Endpoint figure is the shakiest number here — published sources quoted node-hour rates that imply anywhere from $45 to $89/month for a comparable machine, and I could not reconcile them; the conclusion (billed hourly while idle, so wrong for this workload) holds across the whole range, but check the calculator before budgeting. GKE Autopilot's ~$113 assumes the cluster management fee applies, which free-tier credits may offset for a first cluster. Cold-start figures are estimates from model size, not measured. Cloud Run free-tier allowances are per billing account, not per service, so another busy service in the same account eats the headroom that makes these zeros.
